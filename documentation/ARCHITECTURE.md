# معمارية المشروع

`kali.sh` هو المدخل الموحد، ويفوض الأوامر إلى سكربتات Bash صغيرة. `scripts/lib/common.sh` يقرأ ملفات إعداد `KEY=value` محددة من دون تنفيذها. `scripts/lib/qmp.py` يتصل بمقبس QMP داخل مجلد runtime خاص بالمستخدم؛ لا تُمرر كلمة VNC في `argv` أو السجلات.

## دورة التشغيل

1. تُحمّل الإعدادات الافتراضية وملف profile ثم إعدادات المستخدم في `~/.config/kali-virtual-security-lab/config.conf`.
2. تُفحص موارد CPU والذاكرة، ويُكتشف KVM؛ في غيابه تستخدم TCG ما لم يطلب المستخدم KVM صراحةً.
3. يحصل كل مستخدم على مجلد runtime خاص وقفل `flock` واحد؛ يبدأ QEMU والقفل محتفظ به طوال عمره، كما تكتسب عمليات إنشاء القرص وفحصه ونسخه ولقطاته واستعادته القفل نفسه حتى تنتهي.
4. تتحقق هوية QEMU من PID و`/proc/<pid>/cmdline` ومقبس QMP قبل إرسال أوامر الإيقاف.
5. تُحفظ الأقراص وISO والنسخ في مجلد بيانات المستخدم الخاص، ويمنع الإنشاء أي استبدال لملف موجود. تقبل إعدادات القرص وكلمة VNC أسماء ملفات فقط، فلا يمكن لمسار الإعداد الخروج من مجلده الخاص.

## الحدود

العزل هنا على مستوى ملفات الحالة وهوية حساب Linux والعملية والمنافذ المختارة. لا يحول loopback إلى واجهة خاصة لكل حساب؛ أي مستخدم محلي قد يصل إلى منافذ TCP المرتبطة بـ127.0.0.1 إذا عرفها. صلاحيات root تتجاوز العزل. لا يشغل المشروع عدة آلات متزامنة للمستخدم نفسه في النسخة الواحدة.

## QEMU والتخزين

يستخدم القرص `qcow2` مع virtio. التشغيل العادي يقلع من القرص، أما install فيضيف ISO كـCD-ROM ويقلع منه. لقطات QCOW2 داخلية ولا تستبدل النسخ الاحتياطية. تتطلب النسخ والاستعادة توقف الآلة، ويمنع القفل المشترك تداخل QEMU مع عمليات `qemu-img` حتى لو بدأت العمليتان معاً. لا تُحذف الصور أو اللقطات تلقائياً.
